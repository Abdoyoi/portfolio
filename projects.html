AI-Based Wordle Solver

Heuristic search vs Deep Reinforcement Learning · Group project (team of four) · CS21002, October 2026

Description
Wordle is a guessing game where each guess both tries to win and narrows down the hidden word. We built several agents that play it and compared them: entropy, expected-size and minimax search, two simple baselines and a Deep Q-Network (DQN) that learns by trial and error. We tested them on different word lists and under six-guess and four-guess limits.
Technologies
PythonDeep Q-learningHeuristic searchPygameJava SwingAutomated tests
My role
Member of a four-person team. I built the search-based agents: the entropy, expected-size and minimax heuristics. Each one scores every legal guess against the words still possible, plays the best-scoring guess, and then filters the candidates using the colour feedback. The DQN, the playable game and the Java dashboard were built by other team members.
Challenges & what I learned
The three heuristics rank guesses differently, so they trade off quality against speed: entropy needed the fewest guesses but was the slowest (about 147 ms per game on the standard list, compared with about 60 ms for expected-size and 51 ms for minimax). They are also greedy, so they only look one guess ahead and cannot guarantee the best possible play. The best known exact solution averages 3.421 guesses, and my entropy agent averaged 3.672. Across the team’s experiments the DQN beat search under a four-guess limit but won only 46% of games on the largest 12,953-word list, and our report is clear that we could not tell whether too little training or the bigger vocabulary was to blame. This taught me to be careful about what an experiment does and does not show, and to report limitations honestly.

Chess Opponent Move Predictor

Machine learning · Individual project

Description
You enter a chess position and the tool predicts the most likely next move for you and for your opponent, based on each player’s rating. It was trained on games from Lichess, so it predicts what players at that level actually tend to play, not what the best move is. Stockfish’s best move is shown alongside so you can compare the two.
Technologies
PythonMachine learningLichess game dataStockfish
My role
Sole developer: I designed and built it, from preparing the game data to the prediction tool.
Challenges & what I learned
Most chess tools tell you the objectively best move, but real players, especially at lower ratings, often play differently. The challenge was to model human behaviour for a given rating rather than perfect play, and showing Stockfish next to the prediction made the gap between the two visible.

The source code for this project has since been lost, so there is no repository to link. I can explain how it worked in an interview.

Whispr: Offline Messaging App

Java Swing · CS12002 team project (Year 1), extended afterwards

Description
Whispr is an offline messaging application with a Swing graphical interface, written in Java. You can open and reply to chats (with read/unread status), start new chats, edit your profile, manage and sort contacts, search every message by keyword, and save and load everything from text files. The code is split into packages for the model, custom data structures, managers and the GUI.
Technologies
JavaSwing GUILinked lists & queuesHashSetFile I/OObject-oriented designAutomated testing
My role
I planned the team’s meetings and tasks, and I wrote the core of the application: the model classes, the custom data structures, the managers and the first version of the interface. After the module I extended it into a complete application. I used AI assistance (Claude) to connect search, save/load and contact management to the interface, fix bugs, and write the tests, and I am working through that code so I can explain every part.
Design decisions & what I learned
  • Messages are stored in my own linked-list queue with a tail pointer, so adding a message is constant time.
  • Chats are kept in a doubly linked list, so a chat can be unlinked without shifting other items. Chats can be re-sorted by most recent message or by contact name.
  • Contacts use an ArrayList plus a HashSet of phone numbers, so a duplicate number is detected in constant time instead of by scanning the list.
  • Deleting or editing a contact was one of the brief’s “wider implications”. Chats store phone numbers rather than contact objects, so deleting a contact does not break old chats (the user chooses to keep them or delete them too), and changing a phone number re-links the existing chats.
  • Saving writes the user, contacts, chats and messages to separate text files, linked by chat ID. Special characters in messages are escaped, so any text survives a save and load. Testing this found that the first version silently dropped users and contacts with an empty picture path.
  • Search finds individual messages that contain all the keywords, newest first, and opens the chat scrolled to the message.
Testing
32 automated checks on the data structures, contacts, search and the save/load round trip, plus a scripted test that drives the real interface (38 checks: opening chats, replying, searching, editing contacts, saving, loading and deleting).

Secure Login System

C · Individual university project

Description
A login system where users register with a user ID and password and then sign in. Registered users are stored in a hash table so that finding a user stays fast however many accounts there are.
Technologies
CHash tablesAuthentication logic
My role
Sole developer: I designed, wrote and tested it.
Challenges & what I learned
I learned why a hash table gives much faster lookups than scanning through a list of users, and how it works at a low level in a language like C where you manage the details yourself.
